# 开发过程说明（我是怎么做出来的）

> **这份文档解决什么问题**
> `ARCHITECTURE.md` 讲的是"成品长什么样"。
> 但评审真正会问的是：**"你怎么做出来的？为什么是这个顺序？中间出过什么问题？"**
> 本文按时间顺序记录整个过程：每一步做了什么、为什么先做这个、怎么确认它对了、踩了什么坑。
>
> **怎么用**：第 3 节是主线（按阶段讲），第 4 节是三个"卡住过的地方"（最出彩的部分），
> 第 5 节告诉你哪些是 ICD 硬性要求、哪些是我自己的判断（答辩时这个区分很重要），
> 第 7 节是直接可以背的过程叙事脚本。

---

## 1. 一句话概括我的做法

> **我没有按"从上到下写代码"的方式做这个项目，
> 而是按"先让最小闭环跑起来、再一层层加固"的方式做的。
> 每一个阶段都必须先能被观测、再往下走；没有可复现证据的功能，不算完成。**

具体来说：先把不能出错的东西（接口、类型、参数）钉死，
然后让算法层在 PC 上跑通并单测，
再接上任务和消息队列形成闭环，
最后才加保护与展示。
—— 这正好也是 ICD §28「集成顺序」强制要求的顺序，但即使 ICD 不写，也应该这么做。

## 2. 开工前的三件事

### 2.1 先把任务书读成"可执行的约束"

ICD 是一份 `.docx`。我没有直接翻它，而是先把它解出纯文本
（`.docx` 本质是 zip，正文在 `word/document.xml`），存成
`docs/ICD_V1.0_plaintext_extract.txt`。

**为什么值得做这一步**：ICD 里散落着大量"冻结"约束（§3 的类型、§9 的 API、
§10 的转换表、§20 的参数、§22 的顺序、§23 的依赖规则）。
把它们变成可搜索的文本后，我才能在写每一行时回头核对"这条是不是被冻结的"。
**先建立"约束的可检索性"，再动手写代码。**

### 2.2 摸清环境（这一步救了后面所有工作）

第一件事不是写代码，是确认**我能编译吗**。探查结果：

| 工具 | 结果 |
|---|---|
| gcc / clang / cc / make / cmake / ninja | **全部没有** |
| arm-none-eabi-gcc（STM32 工具链） | **没有** |
| git / node / python / winget / choco | 有 |
| 网络 | `api.github.com` 通，但 **`github.com` 与 release 下载不通** |

于是出现了一个非常现实的问题：**没有 C 编译器，ICD §28 阶段 A 的"普通 C 单元测试"就无从谈起。**

我试了两条路，都失败：
- 下载 w64devkit 便携工具链 —— 卡在 `github.com` 连不上；
- `git clone` FreeRTOS-Kernel 源码 —— 同样连不上。

然后换了思路：**国内镜像可达**（清华、阿里、中科大、南大都通）。
最终方案是：

```
pip install ziglang    # 从清华镜像装，98 MB，自带 clang 21 与完整 C 工具链
```

**为什么这个选择是对的**：不需要管理员权限、不动系统环境、
一条命令就得到一个可用的 C 编译器；而且 Zig 自带交叉编译能力，
将来要验证 ARM 目标也用得上。

> **这一段的讲法**：环境受限时，先分清"哪些是必须解决的"和"哪些是可以绕开的"。
> 我要的是"能编译能跑测试"，不是"必须装 gcc"。

### 2.3 建目录：先按 ICD §24 摆好，再决定往里放什么

ICD §24 给了一份"推荐真实文件骨架"。我**原样创建了它列出的每一个文件**
（`Common/types.h`、`Control/pid.c`、`Service/motor_manager.c`、`RTOS/task_*.c` ……），
然后再叠加了自己的目录（`Tests/`、`Sim/`、`tools/`、`docs/`、`build/`）。

**为什么先建目录**：目录结构是架构最便宜的表达形式。
一个 `Control/pid.c` 里不许 include `FreeRTOS.h` 的规则，
写在文档里是约定，画在目录上就是"它连搜都搜不到"。

## 3. 主线：八个阶段

每个阶段我都用同一套纪律：**做什么 → 为什么先做它 → 怎么验证 → 出了什么问题**。

### 阶段 0 · 公共层：把不能出错的东西钉死

**做了什么**：`Common/types.h`（把 ICD §3 的 5 个枚举、§4 的 `MotorData`、
§5 的 `CommandMessage` 一个字段不改地抄下来）、`Common/config.h`（§20 的全部常量）。

**怎么验证**：这两个文件是纯头文件，我确认它们能脱离 RTOS 独立编译 ——
这是后面"算法层能在 PC 上单测"的前提。

**踩的坑（这个坑很典型）**：
我最初在 `config.h` 里写了编译期自检：

```c
#if (RC_PID_OUTPUT_LIMIT <= 0.0f)     /* 错 */
#error "must be positive"
#endif
```

编译不过：**预处理器只能处理整数常量表达式，浮点字面量是非法的。**
我改成 C11 的 `_Static_assert`，结果 clang 又警告：
`_Static_assert` 同样要求整数常量表达式，浮点比较会被当成 GNU 扩展折叠。

**最终处理**：整数不变量留在 `#if`，浮点不变量下沉到
`Tests/test_config.c`，变成"每次构建都会跑的测试"。
**配置错误依然在构建阶段暴露，只是换了一个合法的表达方式。**

### 阶段 A · 算法层：先让 PID 和对象模型在 PC 上跑通

**做了什么**：`Control/pid.c`、`Simulation/virtual_motor.c`，
外加一个 60 行的自制测试框架 `Tests/test_framework.h`。

**为什么先做这个**：ICD §28 把"普通 C PID 单元测试 + VirtualMotor 单元测试"放在阶段 A，
理由很清楚 —— **没有电机、没有 RTOS 的时候，算法层是唯一能离线验证的部分**。
先把它验证掉，后面所有问题都只在"集成"，不会和"算法对不对"混在一起。

**怎么验证**：我为 PID 写了 71 项检查，逐条对应 ICD §7 的七行算法。
其中一条我特意做了"顺序验证"：

```c
PID_Init(&pid, 0.0f, 1.0f, 0.0f, 1e6f, 1e6f);
for (int i = 0; i < 10; ++i) PID_Update(&pid, 2.0f, 0.0f, 0.01f);
TC_NEAR(pid.integral, 0.2f, TOL);   /* 2.0 * 0.01 * 10 */
```

**一个刻意的决定**：ICD §7 标注"算法冻结"，而它**没有条件积分抗饱和**。
我完全可以顺手加上 —— 但我选择**原样实现**，
因为在一个明确写了"冻结"的接口上静默改进，会破坏整份 ICD 作为"接口宪法"的权威性。
我改成了：量化它、记录它、留给 V1.1（见第 4 节的第三个问题）。

### 阶段 B · 服务层 + 仿真适配层

**做了什么**：`Service/motor_manager.c`（数据所有权 + §10 状态机），
以及主机端的 RTOS 兼容层 `RTOS/port_sim/`。

**这里遇到 ICD 的第一处硬冲突**：
- §4 要求 `MotorData.update_tick` 记录时间 → MotorManager 需要读 tick；
- §18 规则 5 允许它用短临界区；
- 但 §23 **禁止 MotorManager include FreeRTOS.h**。

三者不能同时满足。**处理方式不是违反其中一条，而是加一层依赖倒置**：
Common 层只**声明**平台需要提供的原语（`Common/rc_port.h`），
由 `port_sim`（主机）或 `port_freertos`（硬件）各自实现。

**这个决定后来被证明是整个工程最值钱的一处**：
RTOS 任务代码在主机和 STM32 上**一字不改**，
换平台只替换 3 个文件。答辩时这是最值得展开的一条。

**怎么验证**：`MotorManager` 175 项检查，包括
"GetSnapshot 返回的是拷贝，改它不影响管理器"、
"RUNNING→INIT / ERROR→RUNNING / INIT→RUNNING 必须被拒绝"这类边界。

### 阶段 C · 命令系统

**做了什么**：`Service/command_service.c`（Parse / Send / Handle 三分离）、
队列抽象、`RTOS/task_command.c`。

**两个具体的技术判断**：
1. **不用 `strtok`** —— 它有静态内部状态、不可重入，在多任务环境下是隐患；
   自己写了一个把行切成大写 token 的小词法器，并且对"超长 token"
   直接判整条非法，而不是截断后"看似命中"一条错误命令。
2. **不用 `atof` 直接转** —— 用 `strtof` 加 `endptr` 校验，
   保证 `SET_SPEED 1000abc` 这种"前缀合法"的输入被拒绝。

**怎么验证**：252 项检查，覆盖大小写、多余空白、逗号分隔、CRLF、
全角冒号等真实会出现的输入，以及队列满时必须返回 `RC_BUSY` 且计数。

### 阶段 D · 保护层（这里做了一个我自己拿主意的设计）

**做了什么**：`Service/monitor_service.c` + `RTOS/task_monitor.c`。

**ICD §16 说"严重错误 → StopOutput → ERROR"，但没说哪些故障算严重。**
如果按字面把所有故障都当严重，会出现一个荒谬的结果：
**在串口上打错一个字，电机就急停。**

我定了一条判据，并把它写进了代码注释和测试：

> **只有"我们已经不知道电机正在发生什么"才触发保护。**
> 心跳丢失、反馈过期、NaN/Inf、超范围、长期无响应 —— 停。
> 队列满、命令解析失败 —— 只记录，不停机。

**为什么这条值得讲**：它区分了"安全性"和"可用性"。
保护的边界定得太宽，现场结果就是没人敢用这条调试通道。

**时间比较的一个细节**：所有超时判定都写成 `(now - then) > timeout`，
而不是 `now > then + timeout` —— 后者在 tick 回绕时会失效，
这是嵌入式里非常常见的隐性 bug。

### 阶段 E5 · 任务层（这里我撞上了最大的一个坑，见第 4 节问题一）

**做了什么**：5 个任务（`task_control.c` / `task_motor.c` / `task_command.c` /
`task_monitor.c` / `task_debug.c`）+ `Application/app.c`（§22 冻结启动顺序）。

**一个所有权上的细节**：ICD §22 的启动顺序里要求调用 `PID_Init` 与 `VirtualMotor_Init`，
但 §6/§18 又要求 PID 只能被 ControlTask 碰、VirtualMotor 只能被 MotorTask 写。
**我没有把实例挪到 main 里去迁就启动顺序**，而是让每个任务模块暴露自己的初始化函数
（`TaskControl_InitController` / `TaskMotor_InitModel`）。
顺序一点没变，所有权也一点没破。

### 阶段 E6 · 集成测试：跑真实的调度器和真实的队列

**做了什么**：`Tests/test_closed_loop.c` —— 8 个端到端场景，
**跑的是真实的 5 个任务和真实的 FreeRTOS 消息队列**，
不是把模块函数按顺序调一遍。

**为什么这一步不能省**：单元测试永远抓不到"某个任务没被创建""优先级写反了"
"心跳没人上报""队列没人消费"这类问题。它们只在**并发和时序**里出现。

激励方式也很直白：让仿真串口按时间轴注入文本命令，
等价于"有人在终端上敲命令"。

**故障注入用了 `vTaskSuspend` 挂起 MotorTask**，而不是改一个布尔开关 ——
因为前者才是"反馈线真的断了"，后者是"我以为反馈断了"。

### 阶段 E7 · 演示与数据：把曲线变成指标

**做了什么**：`Sim/sim_demo.c`（脚本化激励 + 10 ms 采样写 CSV）、
`tools/analyze_trace.py`（从原始 CSV 算超调/上升时间/整定时间/稳态误差，
并生成 SVG）。

**为什么不用"看一眼曲线"**：肉眼看图不可复现，也无法回归对比。
把"看起来还行"变成"超调 16.11%、整定 570 ms、稳态误差 +0.000"，
才叫工程结论。

**这里踩了一个很小的坑但很典型**：`Start-Process -ArgumentList` 在 PowerShell 里
**不会自动给带空格的路径加引号**，而我的工作区路径里正好有个空格
（`E-control project`）。现象是演示跑完了但 CSV 一个都没有。
改成"设置工作目录 + 传相对文件名"就好了。

### 阶段 F · 硬件预留 + 文档

**做了什么**：STM32 侧的 `port_freertos.c`、`bsp_uart_stm32.c`、
`FreeRTOSConfig.h`（任务优先级**从 `Common/config.h` 引**，
保证仿真和硬件的优先级是同一份来源）、`main_stm32.c`、`Makefile.stm32`。

**我明确标注了"未在本机编译验证"** —— 本机没有 ARM 工具链，这是事实。
把没跑过的代码说成跑过了，是这类交付里最严重的错误。
所以我把"怎么验证"写成了一份 7 步的清单（`BUILD_STM32.md` 第 4 节），
每一步都要求"有观测"才算过。

**文档为什么也按 ICD §26 写**：ICD §26 规定发现问题要走
"提出 → 说明接口/原因/影响/替代方案 → 确认 → 更新 → 同步"的流程。
我全程没有改任何冻结接口，所以把 7 处"新增或澄清"全部写进了
`docs/ICD_CHANGE_REQUEST.md`，每条都带"替代方案"和"为什么选它"。

## 4. 三个真正卡住过的地方（这部分最值得讲）

> 答辩时，"没遇到困难"比"遇到了但解决了"更不可信。
> 下面三条都保留了**现象 → 误判 → 定位手段 → 根因 → 修复 → 验证**的完整链路。

### 问题一：仿真器永远卡在 `tick = 0`

**现象**：闭环节奏的集成测试一跑就挂，40 秒超时。
日志停在 `entering ClosedLoop integration suite` 这一行。

**第一次误判**：我以为是某个任务不阻塞（协作式调度的经典死法）。
于是加了一个"自旋看门狗"，规定某个任务连续被调度 20 万次而时钟不前进就报错。
—— **看门狗没触发，说明不是这个原因**，这个排除反而很有价值。

**第二次误判**：怀疑是测试代码或输出缓冲的问题。
我先给测试程序加了 `setvbuf(stdout, NULL, _IONBF, 0)` 关掉缓冲 ——
因为块缓冲会把"卡在哪一行"这条唯一的线索吞掉。
结果确认卡死发生在启动调度器之后。

**关键的定位手段**：
1. 在调度器里加 tick 追踪，打印 `tick=%lu limit=%lu`
   → 发现**只打印了一次 `tick=0 limit=8000`**，时钟根本没动过；
2. **写一个最小 probe**：两个空任务（一个 10 ms 周期、一个 1 ms 延时）+ tick 上限 1000，
   只链接 `port_sim.c`。→ **同样卡死**，证明与业务代码无关，问题在调度器本身。

**根因**：我把"协作式调度"实现成了"直接调用任务函数"：

```c
s_tasks[best].fn(s_tasks[best].param);   /* 以为任务在这之后会回到调度器 */
```

但 `vTaskDelay` 只是一次**普通函数调用**：它 `return` 之后，
执行流还在任务自己的 `for(;;)` 循环里，于是任务永远回不到调度器。
`s_tasks[best].used = false` 那行"任务结束后回收"的代码根本执行不到。

**修复**：任务需要一个"能被挂起、之后还能从原处继续"的执行上下文，
也就是协程。三个候选：真实线程乒乓交接（平台代码翻倍）、
POSIX `ucontext`（MinGW 不提供）、**Windows Fiber（采用）**。

纤程给了三件正好需要的东西：
① 同一时刻只有一个执行流 → 结果确定、逐拍可复现；
② 切换点只在任务自己调用的阻塞 API 上 → 语义等于协作式调度；
③ 每个任务独立栈 → 任务里的局部变量在阻塞前后正确存活，与真实 FreeRTOS 一致。

**验证**：最小 probe 立刻打印 `scheduler returned at tick 1000`，
随后全套测试一次性通过。

**保留的产物**：那个"自旋看门狗"没有删掉，改成了 20 秒无进展就报
`FATAL: scheduler spin detected` 并退出码 2 ——
把"永远卡住"变成一条有时戳的报错。**排查过程中做的工具，本身就是资产。**

### 问题二：编译报错"看不见"

**现象**：构建失败，但控制台上一片空白，或者只有一句莫名其妙的
`Unexpected token ')'`。

**根因是三层叠在一起的**：

1. **编码层**：Windows PowerShell 5.1 会把**没有 BOM 的 UTF-8** 的 `.ps1`
   当成 ANSI 读。我的构建脚本有中文注释，GBK 误读后某些字节被理解成引号，
   于是解析器看到的是"引号不配对"，报出与实际代码毫无关系的语法错误。
2. **错误流层**：修了编码后，脚本里的 `$ErrorActionPreference = 'Stop'`
   会把**原生 stderr 当成异常抛出**，编译器的报错正文被丢掉，
   只剩一句 "NativeCommandError"。
3. **并发层**：clang/zig cc 在一条命令里编译多个 `.c` 时会**并行**处理，
   多个文件的诊断互相交错，即使看得见也读不懂。

**修复**：
- 构建脚本改成**纯 ASCII 注释**（而不是加 BOM —— 因为加过的 BOM 会被后续编辑工具剥掉，
  那就成了"时好时坏"的隐患。构建脚本本来就不该依赖编辑器编码）；
- 每次编译把输出**重定向到文件再回显**，任何调用方式都能看到真实报错；
- **逐文件编译再链接**，让报错永远可读。

**为什么值得讲**：很多人把构建系统当"外围工具"。
但构建系统一旦不可观测，后面每一次排错都要多花十倍时间。
**可观测性的投入，和写业务代码一样值钱。**

### 问题三：超调比我算出来的大一截

**现象**：我按二阶闭环设计，取阻尼比 zeta = 1.0（临界阻尼，理论上**零超调**），
解出 `kp = 0.18`、`ki = 1.0`。
但实测四组阶跃的超调是 **10.7% ~ 16.1%**。

**排查顺序（先排除最容易错的，再怀疑最不容易错的）**：
1. 是不是参数算错了？→ 上升时间 70~90 ms 与设计值 ωn=10 rad/s 吻合，**推导是对的**；
2. 是不是实现错了？→ PID 单元测试逐行验证过 §7 的七行算法，**实现是对的**；
3. 那问题在哪？→ 用离线工具 `pid_step_simulate` 做**受控对比**：
   同一组增益、同一对象、同一个 `dt`，只切换"条件积分"开关。

| 配置 | 超调 | 整定时间 |
|---|---|---|
| 无条件积分（= ICD §7 冻结行为） | **29.85%** | 0.44 s |
| 有条件积分（V1.1 候选） | **1.99%** | 0.15 s |

**根因**：**问题不在参数，在算法。**
ICD §7 冻结的 PID 只有"积分限幅"，没有"输出饱和时冻结积分器"。
输出早就被限幅了，积分器还在按 `error * dt` 继续长，
目标反向时需要额外时间"爬回来" —— 表现就是超调。

我还写了一个单元测试把这个缺陷**固定成可回归的证据**：

```c
/* 误差已经归零，控制器却仍然输出满幅 100 —— 这就是积分饱和的数值定义 */
TC_NEAR(PID_Update(&pid, 0.0f, 0.0f, 0.01f), 100.0f, 1e-3);
/* 反向误差 -1 持续 1 秒，只能把积分从 100 拉回 99 */
```

（顺带说一句：这个测试我第一版写错了 —— 我用"给一个大的反向目标看输出是否仍为正"
来判断饱和，结果被比例项 `kp*(-1000)` 盖过去了。**是测试写错了，不是代码错了。**
改成"零误差仍输出满幅"才是干净的证据。）

**处理方式**：**没有静默修改冻结算法**，而是把它量化、
写成 CR-001、并给出改进方案与预期收益。

> **这一条是整份工程里最能体现"工程判断"的地方**：
> 遇到不理想的指标，第一反应是"调参数"是新手；
> 能证明"这不是参数问题"、并且**选择不改动被冻结的东西而是记录它**，才是工程。

## 8. 如果重来一遍，我会改什么

诚实地说，有三处可以更早做对：

1. **先写调度器的最小 probe 再写业务任务。**
   我把 5 个任务都写完了才发现调度器是坏的，
   等于在一个错的地基上盖了三层楼。**平台层应该先用最小例子验证。**

2. **一开始就把构建脚本写成纯 ASCII 并逐文件编译。**
   我在编码和并行编译上浪费了两轮返工，而这些是完全可以在第一次就避免的。

3. **先写"从 CSV 算指标"的工具，再写演示程序。**
   我先做演示、后做分析，导致第一版指标是被 STOP 污染过的假数据
   （"稳态误差 +284"）。
   **先定义"什么叫做对了"，再去产出数据，能省掉一次返工。**

这三条有一个共同点：**都是在"验证手段"上省了功夫，后来又补回来。**
所以这份工程最后沉淀下来的最值钱的资产，
其实不是那 4600 行 C 代码，而是 `Tests/`、`tools/`、`docs/` 这三块 ——
它们让"做完了"这件事可以被别人验证。
